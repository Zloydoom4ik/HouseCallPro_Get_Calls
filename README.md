# HCP Calls — выгрузка звонков и записей из Housecall Pro

Скрипт забирает журнал звонков из Housecall Pro и скачивает аудиозаписи разговоров
себе на диск, чтобы их можно было хранить и потом анализировать. Это первая из двух
частей. Вторая — отдельная программа-анализатор (расшифровка + разбор моделью), см. конец файла.

---

## 1. Как это вообще работает

У Housecall Pro **нет** публичного API для звонков. Но их собственный сайт где-то же
берёт эти данные — значит, есть внутренний API, к которому обращается страница
`pro.housecallpro.com/app/voice`. Мы разобрали в DevTools, что он делает, и повторяем
те же запросы из скрипта под тем же логином.

Данные лежат в **двух местах**, и мы ходим в оба:

```
                    ┌─────────────────────────── наш скрипт (collect.py) ───────────────────────────┐
                    │                                                                                │
   1) СПИСОК звонков │  GET pro.housecallpro.com/alpha/voice/call_logs   + cookie сессии             │
      (у Housecall)  │  ← JSON: только звонки нашей компании, в каждом — готовая ссылка на запись    │
                    │                                                                                │
   2) ФАЙЛ записи    │  GET api.twilio.com/.../Recordings/RE....wav      (без всякой авторизации)     │
      (у Twilio)     │  ← сам .wav файл                                                              │
                    │                                                                                │
   3) СОХРАНЯЕМ       │  метаданные → SQLite (hcp_calls.db),  аудио → файлы на диске                  │
                    └────────────────────────────────────────────────────────────────────────────────┘
```

Важные факты, которые мы выяснили руками:

- **Телефония Housecall Pro построена на Twilio.** Записи отдаёт напрямую Twilio
  (`api.twilio.com/2010-04-01/Accounts/AC…/Recordings/RE….wav`), а не сервер HCP.
- **Ссылка на запись работает без пароля.** Twilio отдаёт файл любому, кто знает
  точный адрес. Но получить *список* записей у Twilio нельзя — для этого нужен секретный
  ключ аккаунта, а он у Housecall Pro. Поэтому список мы всегда берём у HCP.
- **«Только наши звонки» задаёт не адрес, а cookie.** Адрес `call_logs` одинаковый у
  всех клиентов HCP. Сервер по cookie понимает, кто мы, и отдаёт звонки только нашей
  компании. Поэтому весь доступ держится на одном cookie — `_housecall-web_session_with_domain`.
- **Записи живут ~6 месяцев.** С 01.01.2025 HCP удаляет всё старше полугода. У удалённых
  записей в JSON стоит `discarded_at`, и файла в Twilio уже нет (404). **Поэтому выгрузку
  надо запустить как можно скорее** — то, что старше полугода, уже не вернуть.

## 2. Что за запросы мы делали в консоли и что вернулось

Мы дёрнули `call_logs` с разными параметрами прямо из вкладки браузера. Ответ — JSON
с такими полями верхнего уровня:

| поле | что значит |
|------|-----------|
| `object` | тип ответа, тут `"list"` (список) |
| `page` | номер текущей страницы |
| `page_size` | сколько звонков на странице |
| `total_pages_count` | **всего страниц** (было ~34 859 при `page_size=5`) |
| `total_count` | **всего записей в журнале за всю историю** — было **174 294** |
| `data` | массив звонков этой страницы |
| `url` | служебный путь, нам не нужен |

**`total_count = 174 294` — это все строки журнала**, а не только записанные разговоры.
Сюда входят входящие, исходящие, пропущенные, голосовые — всё, что показывает Call Log.
Из них реально скачиваемых аудиофайлов гораздо меньше: только звонки с записью и только
за последние ~6 месяцев (остальное удалено).

Что ещё показали те запросы:
- **Страницы листаются параметром `page=1,2,3…`** (проверили: ID звонков на стр.1 и стр.2
  разные). Скрипт так и делает.
- **`page_size=500` сервер отклонил (400 Bad Request).** Большие страницы нельзя.
  Поэтому берём `page_size=80`, как сам сайт.

## 3. Какие данные получаем по каждому звонку

Запрос идёт с `expand[]=call_dispositions,customers,recordings,voicemails` — это значит
«приложи к каждому звонку ещё и клиента, итоги, записи и голосовые». По звонку приходит:

- `uuid` (`vcl_…`) — ID звонка в Housecall Pro. **Наш главный ключ.**
- `sid` (`CA…`) — тот же звонок в Twilio.
- `from`, `to`, направление, статус, длительность, дата.
- `customer` (`cus_…` + имя) — **связь с клиентом.** По этому ID через официальный API
  HCP можно потом подтянуть заказы клиента и понять, во что вылился звонок (деньги/не деньги).
- `call_dispositions` — итог/причина звонка, которые проставляют сотрудники. Готовая
  «ручная разметка» — с ней удобно сверять выводы модели.
- `recordings.data[]` — список записей. У каждой: `sid` (`RE…`), `status`, `duration`,
  `discarded_at`, и **готовые `wav_url` / `mp3_url`**. Записей может быть несколько
  (например, при переводе звонка).
- `voicemail` — голосовое, если есть.

Мы **сохраняем весь JSON звонка целиком** (поле `raw_json`), поэтому, даже если какое-то
поле сейчас разобрано неточно, ничего не теряется — анализатор всегда сможет перечитать
исходные данные.

## 4. Архитектура хранилища — и почему так

**Аудио — файлами на диске. Метаданные — в базе. Крупные бинарники в БД не кладут.**

```
data/
├── hcp_calls.db                     ← SQLite: метаданные + что уже скачано
├── recordings/2026/09/29/RE....wav  ← аудио, разложено по дате звонка
└── raw/page_00001.json              ← сырой ответ каждой страницы (страховка)
```

### Почему сборщик пишет в SQLite, а не сразу в Postgres

Хотя Docker/Postgres у тебя есть, **сборщик специально сделан на SQLite**:
- он встроен в Python — **работает сразу, без поднятия контейнеров и без драйверов**
  (а на очень свежем Python 3.14 бинарные драйверы Postgres могут ещё не собраться);
- задача сборщика — тупо и надёжно скачать файлы, пока их не удалили. Чем меньше у него
  зависимостей, тем меньше поводов не запуститься;
- **схема SQLite один-в-один совпадает с Postgres** (см. `schema_postgres.sql`), поэтому
  перелить метаданные в Postgres позже — это простой импорт, а аудиофайлы вообще никуда
  не переезжают.

### Где Postgres

Postgres поднимаем в Docker (`docker-compose.yml`) **под анализатор** — вторую программу.
Ей нужен нормальный SQL для выборок, JSONB, связи с расшифровками и результатами разбора.
Разделение простое: **сборщик копит сырьё, анализатор работает с базой знаний.**

### Сколько места

Стерео-WAV ≈ **2 МБ на минуту** разговора. Тысяча звонков по 3 минуты ≈ 6 ГБ. Для архива
можно потом пережимать в FLAC/Opus (в разы меньше без потери разборчивости для расшифровки),
но исходники лучше сохранить.

## 5. Схема базы (SQLite сейчас / Postgres потом — идентичны)

- **`calls`** — звонки. Ключ `uuid` (`vcl_…`). Плюс `raw_json` со всем исходным JSON.
- **`recordings`** — записи. Ключ `sid` (`RE…`). Хранит ссылки, путь к скачанному файлу,
  и `download_status` (`pending`/`downloaded`/`failed`/`discarded`).
- **`sync_state`** — служебное: когда был последний запуск.
- (в Postgres добавятся **`transcripts`** и **`call_analysis`** — их заполняет анализатор.)

Идемпотентность: оба ключа `UNIQUE`, запись идёт через `INSERT … ON CONFLICT DO UPDATE`.
Повторный запуск **не двоит** данные, а обновляет (у звонка со вчера могли появиться
запись, итог или привязка к клиенту).

## 6. Установка и первый запуск

```bash
cd C:\Dev\retail\hcp_calls_scripts
py -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env          # при желании поправить настройки
```

**Cookie** (доступ к аккаунту; делается один раз):
1. Смени пароль в Housecall Pro и войди заново — старые сессии протухнут, скопируешь свежую.
2. F12 → вкладка **Application** → слева **Cookies** → `https://pro.housecallpro.com`.
3. Найди `_housecall-web_session_with_domain`, двойной клик по **Value**, скопируй.
4. Вставь значение **одной строкой** в файл `secrets\hcp_cookie.txt` (без имени, без кавычек).

**Проверка полей** (ничего не пишет, только показывает структуру одного звонка):
```bash
python probe.py
```
Сверь имена полей с тем, что разбирает `collect.py`. Если что-то называется иначе —
поправим (но `raw_json` всё равно сохранит всё).

**Первый полный проход** (тянет историю за ~7 месяцев и качает все живые записи):
```bash
python collect.py --full
```
Это займёт время (паузы между запросами специально стоят). Прервётся — просто запусти
снова, продолжит с того же места.

Полезные режимы:
```bash
python collect.py --metadata-only   # сначала быстро собрать метаданные, файлы потом
python collect.py --downloads-only  # только докачать записи из БД
python collect.py --max-pages 3     # для проверки: только 3 страницы
```

## 7. Ежедневный запуск

Дальше хватает обычного инкрементального прохода `python collect.py` — он берёт только
новое и останавливается, дойдя до уже известных звонков.

**Windows (Планировщик задач):** создать задачу, действие — запуск `run_daily.bat`,
триггер — ежедневно ночью. Лог пишется в `data\collect.log`.

**Linux (если перенесёшь на сервер), cron:**
```
30 4 * * *  cd /opt/hcp_calls && venv/bin/python collect.py >> data/collect.log 2>&1
```

Сессия на 14 дней и продлевается при каждом запуске, так что ежедневный крон держит вход
живым сам. **Playwright не нужен** — хватает обычных HTTP-запросов.

## 8. Если что-то сломается

Скрипт не «молчит», а падает с понятным кодом и шлёт уведомление (в Telegram, если задан
в `.env`, иначе в консоль/лог):

| код | что значит | что делать |
|-----|-----------|-----------|
| `2` | **сессия истекла** (401 или пришла страница логина) | заново скопировать cookie (шаги из п.6) |
| `3` | **API изменился** (в ответе нет ожидаемых полей) | прислать мне — поправим разбор |
| `1` | прочая ошибка | смотри лог |
| `0` | всё ок | — |

- **429 / 5xx** (сервер перегружен/лимит) — скрипт сам делает паузу и повторяет,
  уважая заголовок лимита. Ронять из-за этого не будет.
- **Удалённые записи** (`discarded_at`) помечаются `discarded` и не качаются.
- **Сырые ответы** лежат в `data/raw/` — если что-то разберём неверно, можно переразобрать
  без повторного обращения к серверу.

## 9. Важные оговорки

- **`/alpha/` — внутренний API HCP.** Он не документирован и может измениться без
  предупреждения. Скрипт это переживёт (остановится с кодом `3`), но иметь в виду стоит.
  Разумно спросить поддержку HCP, нет ли официального способа выгружать записи — это надёжнее.
- **cookie = доступ к твоему аккаунту.** Файл `secrets/` в git не коммитится и никуда не
  выкладывается. Скрины с cookie/токенами тоже.
- **Нагрузку держим вежливой:** паузы между запросами, без параллельных загрузок, лучше
  ночью. Это и про стабильность, и про то, чтобы не мешать их сервису.

## 10. Вторая часть — анализатор (план, отдельная программа)

Когда записи копятся, отдельный процесс разбирает их из базы:

```
recordings (download_status='downloaded')
   → расшифровка (Whisper / Deepgram, с разделением на говорящих по стерео-каналам)
        → transcripts (текст + реплики по ролям и таймкодам)
   → разбор языковой моделью
        → call_analysis (краткое содержание, итог, тон, темы, флаги: грубость,
                          упущенный апселл, невыполненное обещание перезвонить и т.п.)
   → связка с заказами через официальный API HCP по customer_uuid
        → отчёт: какие звонки принесли деньги, где теряем клиентов, как работают операторы
```

Стерео-канал здесь ключевой: оператор и клиент записаны раздельно, поэтому «кто что
сказал» известно точно, без угадывания. Отсюда — честная статистика по операторам
(кто сколько говорит, перебивания, паузы) и качество расшифровки.
